# Sundown app contributor guide

## What this repository is

Sundown is a native macOS SwiftUI client for Claude Code. It is intentionally a thin client: it presents hosts, sessions, streamed transcript items, prompts, and settings while `../tether-server` owns Claude Agent SDK queries and long-lived session state.

This repository builds on its own. Clone it, open `Sundown.xcodeproj`, and build:

- `SundownKit/Package.swift` depends on the `TetherProtocol` package published by `AFRUITPIE/tether-server`, pinned by version. The generated sources are committed there, so nothing has to be generated to consume them.
- The app carries no server and installs nothing. Every host has Node.js 18 or later, and runs tether-server's npm package with the first `npx` on its login shell's PATH: `npx --yes tether-server@<version> connect`, at the version this app pins. A host without it fails to connect, with the shell's own error.
- `ServerRelease.version` (`Bootstrap.swift`) is the server this app runs, the release its protocol package is pinned to. Bump both together, after that version has been published.

`tether-server` is public, so SwiftPM can resolve the protocol package without credentials. The app repository remains private.

### Local development (both repositories side by side)

With a `tether-server` checkout beside this one, the app builds against it and no release is involved:

- `SundownKit/Package.swift` takes the protocol package from `../tether-server` by path, so a protocol change is seen on the next build, in Xcode and in `swift test` alike.
- To run that checkout's server, set This Mac's Server Command (Settings ▸ Hosts ▸ Advanced) to `<bun> run <path>/tether-server/src/cli.ts connect`, with bun's and the checkout's full paths. A host with a Server Command runs it as it is.
- A path dependency has no pin, so SwiftPM empties `Package.resolved`. Both copies are marked `git update-index --skip-worktree` in this clone so that churn stays out of commits; `--no-skip-worktree` before bumping the pin.
- The server's manifest names its package `tether-server`, the same as the folder: Xcode keys a local package by that name and a remote one by the folder-derived identity, and the product lookup fails when they differ.
- `SUNDOWN_USE_RELEASE=1` makes SwiftPM use the published package at its pin instead, which is what CI and a fresh clone get.

Work on local branches and commit there; releases, pin bumps and PRs happen together when the owner asks to ship: release the server, bump `ServerRelease.version` and the pin, then open the PRs.

## Runtime flow

1. `AppModel` creates a `HostConnection` for each configured host and initiates connections.
2. `HostConnection` asks the host's shell, interactive (`$SHELL -ilc`, stdin empty), for its PATH, between markers so whatever its rc files print is ignored; that is where people set PATH (`.zshrc`, `.bashrc`, `config.fish`: nvm, mise, a `claude` wrapper). Then it runs `npx … tether-server@<version> connect` under the login shell (non-interactive, since an rc file's output would land in the JSON-RPC stream) with that PATH, locally or through system `ssh` (a host's Server Command instead, as it is), and sends the PATH in `initialize`'s `env`, which is how a daemon already running with another PATH finds this client's `claude`. A PATH in the host's Environment wins. A shell that doesn't answer in 10 s (an rc file that `exec`s another shell unguarded, or waits for input) leaves the login shell's PATH, said in the connection log. There's no check first and nothing to install or update: a new app runs its new version, and the daemon moves onto it once its running chats finish.
3. `RPCClient` performs the initialize handshake and carries newline-delimited JSON-RPC.
4. `HostConnection` loads the host catalog, maps summaries to stable `ThreadModel` instances, subscribes with `afterSeq`, and batches streaming deltas to roughly one UI update per frame. `RPCClient` holds streamed output for up to a frame and sends anything else at once, with what came before it; `HostConnection.route` applies each batch, joining a reply's consecutive text deltas into one.
5. `ThreadModel` applies snapshots and notifications. SwiftUI renders its cached top-level items, rows, turns, tasks, pending requests, and status.

The daemon, not the app, owns live Claude queries. Closing or disconnecting the app must not end a turn. Reconnection must resume from the last sequence number and reload history only when replay reports a gap.

## State and concurrency invariants

Performance explanations in this guide record earlier experiments on particular workloads and
system versions. They are hypotheses to revalidate, not restrictions on investigating a problem.
Compare alternatives in the running Release app, including long individual turns and scrolling
through loaded history; a parsing or layout micro-benchmark alone does not establish an interaction
improvement. Preserve state/concurrency correctness and native SwiftUI behavior, and revert
experiments that regress either. Prefer simplifying the implementation when measurements support it.

- `RPCClient` is an actor. UI stores are `@MainActor @Observable`; keep network/process work off the main actor and UI mutations on it.
- Do not create or insert observable models from a SwiftUI `body`. Resolve selections when state changes, then render existing models.
- Keep one `ThreadModel` identity per `(host, threadId)`. Replacing it loses subscriptions, pending prompts, and scroll continuity.
- A thread opened before its host connects is deferred through `openRequested`; do not turn that normal race into a permanent “Not connected” error.
- Apply `historySeq`, `lastSeq`, and `afterSeq` consistently. A history snapshot and its live tail must neither overlap nor leave a gap.
- Server requests can be answered by more than one attached client. Preserve the once-only continuation guard and remove prompts on `serverRequest/resolved`.
- Streaming deltas are intentionally coalesced. Do not reintroduce one full transcript invalidation per token. `ThreadModel` appends a reply's text in place (the transcript and the item's box each own a copy); never rebuild an item from a copy per delta. The daemon never sends `HostConnection.unreadNotifications`: take a method out of that list before reading it.
- A `ForEach` element is exactly one view, so SwiftUI counts elements without building them: a row whose body could be none or several (a `Group` around a `switch`, an `EmptyView` case) is wrapped in a stack. Check with the launch argument `-LogForEachSlowPath YES` and `log show --predicate 'subsystem == "com.apple.SwiftUI"'`; what's left at launch (`Range<Int>`, `SubviewsCollection`, `StackItem`, `Effect`) is SwiftUI's own.
- Keep expensive derived work out of view bodies. Transcript rows, child lookup, Markdown parsing, and diffs have caches for a reason.
- `ThreadModel.rows(_:)` is built a turn at a time: a finished turn's rows are kept and only turns from the first changed item (`refoldFrom`) fold again; a prepend, reload or trim refolds everything. Only the current Tool Calls folding is held. A subagent's items bump `childrenVersion`, not `itemsVersion` (except edits, which count in their turn's edits). `IncrementalRowsTests` holds it equal to folding everything at once. Edit line counts are made off the main actor (`FileChange.changes(ofCallsIn:)`) when a page arrives and when an edit finishes; `rows(_:)` only looks them up.
- A chat no window shows (not in `openRequested`) keeps only its last page once idle with nothing pending: followed chats are unloaded and unsubscribed, live ones trimmed (`ThreadModel.trim`) on leave and after each turn (`HostConnection.afterTurn`), keeping `lastSeq`, the turns and running tasks, so the stream goes on without gap or overlap. An older page goes in only if the item it was asked before is still first. An older page is asked for when the trigger row at the top of the transcript appears (`OlderHistoryTrigger`, one request in flight at a time) and goes in above the reader, whom the bottom `defaultScrollAnchor` keeps on the row they were reading.
- Parsing and decoding stay out of bodies and off the main actor. `MarkdownView.parse` and `MarkdownCache.inline` are nonisolated; `MarkdownCache.prewarm` parses the replies at either end of a chat as it opens and as an older page goes in. `MarkdownCache.recent` holds at most 400 entries and 4 MB of text, least recently used out first, and a reply only once it has stopped streaming. Attachments are prepared off the main actor (PNG, JPEG, GIF and WebP up to 1568 px on the long edge sent as they came, anything else redrawn at most 1568 px, a photo as JPEG), and Send waits for them. Prompts' images are decoded at 480 px into an `NSCache` keyed by message and part. Find keeps each row's search text while the bar is open and searches 100 ms after the last change, off the main actor. A diff draws one `Text` per run of same-kind lines.
- After a turn the chat list fetches the latest `recentChatsLimit` chats and merges them; connecting and explicit actions fetch the whole list, which replaces the one held (only chats not yet written are kept).
- `ThreadModel.title` and `taskEntries` are stored, not derived from `items`: anything the sidebar, toolbar or tab chrome reads must not change per streamed delta. Only `TranscriptView` and its rows read `rows`/`items`.
- A view takes the narrowest model it needs, and each tab and popover is its own view, so a delta redraws at most the transcript and what's open.
- State that changes every frame of a resize or an animation (the transcript's scroll position) lives in a view whose body holds no rows: `TranscriptView` owns the scroll state and `TranscriptContent` the rows. No closure goes in the environment (Apple: not even wrapped in a struct): an action is a struct holding the window weakly, equal when it's the same window, that calls a `WindowModel` method (`InspectSubagentAction`); a new closure on every shell update redrew every tool call.
- Persisted preferences are plain stored properties on `AppModel` saved through `Stored`; where the last window was lives under its own key (`LastWindow`), and no key is written with bytes it already holds. Host environment values are read from the Keychain only for hosts `Stored` lists, just before each connects. No `@AppStorage` inside an `@Observable`. The app-wide values views read (`appearance`, `textScale`, `openFilesWith`, `readingWidth`) are set once per scene (`Scene.appEnvironment`); a preview sets them with `View.appEnvironment`. Custom environment values are `@Entry`; `@Bindable` only where a binding is made.
- Composer drafts (`AppModel.drafts`) live in a file of their own (`Drafts.json` in Application Support, `DraftStore`), go when their chat is deleted, are not observed, and are written a second after typing pauses, off the main thread and only when changed (`DraftQueue`; quit writes synchronously): observed, every keystroke redrew every composer in every window. A composer reads its draft when it appears; text put in from outside (Shortcuts' Start a Chat) goes through `deliverDraft`, a token each composer showing that key applies once.

- A lost host retries on `ReconnectBackoff` (2–16 s, then 30 s, 5 min, 15 min, jittered); an SSH host off the network waits for `NetworkPath`; wake, a network change and Reconnect retry at once (`retryNow`). SSH shares one connection per host (`~/.ssh/tether-%C`, `ControlPersist` 60 s), and the server check is made once a session. Back on the same daemon only the chats reload. The hosts windows show connect first, the others once those are up (at most 5 s) or when a window shows one.
- Slash commands are fetched only when someone looks for one (a typed `/`, the + menu), never because a chat is shown: the daemon starts a Claude Code process per directory to answer. `HostConnection` keeps them until the chat's turn ends or a reconnect. `RPCBudgetTests` holds how many requests connecting, opening and switching chats send; lower a budget when a change sends fewer.
- Task events aren't kept with history, so a Workflow call with no live task (a reload, an older page, a followed chat, a replay gap) has its run read with `workflow/read` by the run id in its launch receipt (`HostConnection.loadWorkflow`): one request in flight per run, a finished run read once per connection and not again (a deleted chat, or one reloaded after a replay gap, lets go of its finished runs; one merely left keeps them, so reopening reads nothing), and again every 5 s while the Tasks tab shows a run still going that this client isn't told about (`TasksPane`, for the workflow selected in any column, so its report and an agent's detail both stay current). An agent's transcript is `workflow/agentItems`, read while its detail is shown, again when its snapshot changes (at most once a second), and kept with the chat once the agent has finished. A daemon without these methods is asked once per connection. `ThreadModel.workflowRuns` is stored and assigned only when a run changes; the chat's rows read it, never `tasks`. A run is built and a script's `meta` read only in `ThreadModel` (once per call, a script without one included), never in a view body or a row's search text, which uses the name the call gives or the one its script was read for (`WorkflowScript.searchName`). A run that has ended settles the agents it last heard of as running or waiting: done when it completed (its last progress can come after the finish, or not at all), stopped when it stopped, failed or can't be said (`unknown`, a cut-off run). Agents' states are read as the CLI names them (`start`, `progress`, `done`, `error`, `skipped`, `queued`, `cached`…, and `skipped: true`), whether the daemon passes them through or names them itself. An agent's transcript read for the chat goes with its workflow's call when the chat is trimmed. `Tests/SundownKitTests/Fixtures` holds a real run (`typo-check`: its task messages, its call and an agent's transcript), which `WorkflowCaptureTests` replays.

## UI and HIG decisions

The product should feel like a standard current macOS app. Prefer native SwiftUI components and behavior over custom chrome. Check the relevant Apple Human Interface Guidelines and API documentation for every interaction or presentation change.

- Target the current project baseline (Xcode 27, Swift 6, macOS 27+). Do not add compatibility shims for older systems unless requested.
- SwiftUI only. AppKit is used where SwiftUI has no API, and only there: a Copy button writing the Clipboard and Show in Finder (`Clipboard.swift`; SwiftUI's `copyable` answers only Edit ▸ Copy, and Apple's documentation says a custom Copy action writes `NSPasteboard`), the Dock's badge and menu and the app delegate they need (which also says whether the app is in front, as the scene phase doesn't on the Mac), opening a file in a chosen editor (`openURL` opens only in the default app), help tags on glass (`glassHelp`), wake and quit (`AppModel`), a message's text (`MarkdownTextView`: SwiftUI has no selection spanning views, so one `Text` per block selected a block at a time, and one `Text` for a whole reply ignores paragraph styles, losing lists' and quotes' indents), and the message field (`ComposerTextView`: SwiftUI's rich `TextEditor` makes every change to its text from code an undoable replacement of the whole text, so styling as you type broke Undo). A fix is made with SwiftUI's own modifiers, never by reaching into the AppKit views SwiftUI builds; say why before adding any AppKit.
- Let system layout and intrinsic sizing work: a row of buttons that may not fit is a `ViewThatFits` (the plan card's stack at the trailing edge), a list's markers share the width of its widest, a bar over a scrolling form is a `safeAreaBar`, and `fixedSize` holds only the axis that must hold. Avoid hand-computed geometry, arbitrary fixed production sizes, and `.fixedSize()` as a general layout repair. Markdown's blocks are plain stacks too: custom layouts measuring each block's text once per width (after swiftui-prose) laid a reply out about 20% faster in `MarkdownBenchmark`, but resizing the Release app measured the same either way (2026-10-04), so they were removed. Fixed frames in previews and small icon/status geometry are fine.
- SwiftUI's `help` shows nothing on a control drawn over Liquid Glass on macOS 27: the glass's own view is under the pointer. Such a control takes `glassHelp` (`Clipboard.swift`): a transparent AppKit view with the tag, which passes every click through.
- Liquid Glass belongs to controls: toolbar controls, composer, and prompt cards. Transcript content uses ordinary fills, and the status strip (information, not a control) the bar material. Never stack glass on glass; controls inside a glass card use standard bordered styles. Glass that comes and goes does it the glass's way: a prompt card `materialize`s. The plain native multiline editor has a padded interactive glass surface; Add and Send/Stop are native glass buttons. Dimming goes on the content under the glass, never after `glassEffect`. Cards share one corner radius (`Layout.cardCornerRadius`). Colors are semantic styles (`.fill`, `.tint`, `.windowBackground`).
- The shell is `NavigationSplitView(columnVisibility:) { SidebarView } detail: { DetailView }`, no declared sizes, and no `.inspector`. `DetailView` switches on `WindowModel.tab` (each window's own, restored with `@SceneStorage`): Chat, Tasks and Diff, chosen with a segmented `Picker` in the toolbar's center (`.principal`); New Chat always shows Chat. Not a `TabView`: in an active window its content lost the toolbar's scroll edge effect (text under the toolbar stayed crisp; inactive, or with the picker, it blurs), and its tabs hid the window's title. No `GeometryReader` or preference keys; no `.id()` on containers other than `ThreadView(...).id(thread.id)`, inside `DetailView`'s chat `ZStack`: when the detail column's root view changes identity, SwiftUI rebuilds the column's toolbar items and they fade in on every chat switch.
- Every toolbar item is unconditional: never an `if`/`switch` around a `ToolbarItem`. Something unavailable is disabled, not removed, so nothing moves when the selection changes. The toolbar is identified (`.toolbar(id: "chat")`) and customizable (`ToolbarCommands`, View ▸ Customize Toolbar…), so Plan Usage (`.defaultCustomization(.hidden)`) can be added. AppKit keeps identified toolbars of the same identifier in step across windows by index; when two windows' items differed for a moment (the old inspector's toggle) it threw (`-[NSToolbar _itemAtIndex:]`, `_currentItems`), so every window must declare exactly the same items.
- The trailing `.inspector` was removed (2026-10-04). On macOS 27 `NavigationSplitView` plus `.inspector` throws "more Update Constraints in Window passes than there are views" whenever showing a column forces the window to grow (Apple's: https://developer.apple.com/forums/thread/836901), counts the inspector's minimum width twice in the window's, and every workaround (window and column minimums, zero-minimum frames, a staged minimum, attaching it to the detail) traded one bug for another. Its panes became the Tasks and Diff tabs and the toolbar's Context, MCP and Plan Usage popovers (`ChatPopoverButton`, a Form at a fixed width and its content's height, `popoverSize`).
- The sidebar is the system's: its own toggle (it animates) and `SidebarCommands()`. No window or column minimum, no zero-minimum frames, no custom sidebar toggle; New Chat is File ▸ New Chat (⌘N) only. Content reports its true minimum width (the composer's plain stacks, New Chat's row through `ViewThatFits`), so the window stops shrinking where the content would clip.
- Measured on the plain shell (Debug, macOS 27, with the inspector): the window bottoms out at 277 pt with the sidebar hidden, 495 with it shown. A window opened with the sidebar already collapsed puts the system sidebar toggle in `»` until the sidebar is toggled, however wide the window (a bare split view does it too), so `RootView` binds `columnVisibility` for this alone: every new window opens with the sidebar shown, rather than as the split view's autosave last left it (2026-10-06). The Settings window's sidebar has no toggle (`.toolbar(removing: .sidebarToggle)`), as System Settings' doesn't.
- The transcript is one `LazyVStack` (`TranscriptContent`, with `.scrollTargetLayout()`) holding the older-history row, every row and the tail, in a `ScrollView` with `.defaultScrollAnchor(.bottom)` (with `.top` for `.alignment`, so a short transcript sits at the top rather than pushing the top edge effect down the window) and `.scrollPosition`. No anchor switching, no hand-kept place, no animation on the scroll view. Sending from this window and a chat's first load `scrollTo(edge: .bottom)`; Jump to Latest is offered once the reader is more than a container's height from the end (one `onScrollGeometryChange`) and the last row isn't on screen (`onScrollTargetVisibilityChange`): the content's height counts rows not built yet at the lazy stack's estimate, and alone it offered Jump to Latest at the end. Find and Previous/Next Prompt `scrollTo(id:)` rows by their ids.
- Toolbar, leading to trailing: the system's sidebar toggle (in the sidebar while it is shown; in the detail toolbar once hidden, going to `»` below roughly 320 pt), the title and subtitle, the Chat/Tasks/Diff picker in the center, then model, effort and permissions (one `.primaryAction` item, trailing, which collapses into `»` when the window is narrow), then Context and MCP (and Plan Usage when added), each a popover. Context's icon is SF Symbols' `circle` (black weight) drawn round as far as the context window is full (a variable value in `.symbolVariableValueMode(.draw)` with `.symbolColorRenderingMode(.gradient)`, as the SF Symbols app shows it, `ContextGauge`; the primary color, yellow from 70%, red from 90%, empty while unknown) (a drawn `Gauge` kept the button out of its neighbours' capsule): `ThreadModel.contextFill`, asked for (`thread/contextUsage`) after each turn ends while the chat is loaded on its host, and when the breakdown opens; empty until then. The toolbar's scroll edge effect is the automatic one. Find in Chat's bar is a top `safeAreaInset`, not a `safeAreaBar`: a top bar, even empty while Find was closed, took the edge effect from the toolbar, so text scrolled up under the title and tabs unblurred. New Chat is not in the toolbar: File ▸ New Chat (⌘N). Model and effort are one item (`ModelEffortButton`, the model's name as text alone) opening a popover (`ModelEffortForm`: the models as rows, each with Claude Code's description under its name and a checkmark on the chosen one, in Claude Code's order and all of them, since a host's `modelPicker` decides which it lists; Fast Mode as a switch in a section of its own; and effort as a slider with a tick per level, its name above, "Medium (Default)" on Claude Code's own level, which sets it back to unset); permissions is a button opening a popover of the modes, rows like the models' with the mode's symbol and summary (`PermissionsButton`, `PermissionsForm`, `ChoiceRow`), not a menu, so it shares a capsule with its neighbours. Customize Toolbar also offers the model as the sparkle alone (`modelEffortIcon`, hidden by default), which can share one too. Every item after the tabs has the default placement (no `.primaryAction`), so Customize Toolbar can move it anywhere; a flexible spacer keeps them trailing and a fixed one groups them, and people can drag in spacers of their own (an explicit placement pins an item to its region). Model and Permissions are titled so (their labels' titles, which the palette and » menu read; the model's `ValueLabelStyle` draws its name instead), and the palette also offers Session (model and permissions) and Chat Info (Context, Plan Usage, MCP) as `.navigation`-style `ControlGroup`s in one capsule, as Mail offers Reply, Reply All and Forward together and apart. Adjacent items merge into one capsule only when they're buttons with SF Symbol icons (`variableValue` included); a menu, a text label or a custom-view icon keeps its own (scratch-app test, macOS 27). They stay in the toolbar: putting them in the message field was tried and dropped. Never change which menus one toolbar item holds: that tripped an AppKit toolbar assertion (`_currentItems`); and `toolbarItemHidden` hid nothing on macOS 27. Each menu's label says its choice ("Permissions, Don't Ask"). - A tool row is words first, starting at the reply's leading edge: a verb in the tense its status calls for, then what it acted on (a file's name, a search), with no kind icon; a command is only "Ran a command", its line in the help tag and the opened row, since a shell line on every row is more than a reader wants, and the status (a gray glyph when it went wrong; never a spinner: a running call's words shimmer, `ActivityLabel`, while its turn runs or it runs in the background), then the disclosure chevron right after the words. A subagent's row has the same chevron and opens it in the Tasks tab. So does a dynamic workflow's ("Running workflow review-diff", then "Ran workflow review-diff"), which is always a row of its own (never folded into a run of calls, and lifted out after a turn's Worked For): its call comes back at once with a launch receipt while the run goes on for minutes, so its tense and its shimmer follow the run (`WorkflowRun.status`), not the call or the turn; how far it has got and what it did are Tasks' (the row opens it), never the chat's, which only says, in gray under the row, why it failed or stopped. It has no detail in place (no script, no receipt); its context menu has Copy Script and, while it runs, Stop Workflow; in Tasks, Copy Script is also in its detail's header, and Stop above its agents' column. A workflow agent's last call (`StructuredOutput`, handing its result back to the script) reads "Returned its result", and opened shows that result as JSON. Calls stay compact by default; expanded groups offer Expand All/Collapse All, separators, and labeled Input/Command/Output sections with full Copy controls. A running call's row says "Running" after its words (`accessibilityLabel { label in … }`): each row is a disclosure triangle, whose value is only whether it's open, so a status set as the value never reached VoiceOver. UI tests find these rows as `disclosureTriangles`.
- A message's text is one selectable text view (`MarkdownTextView`), so a selection runs across its paragraphs, headings, lists, quotes, code and tables, and Copy puts plain text on the pasteboard (list markers as "• ", a blank line between blocks, table cells tab-separated, `MarkdownNSTextView.plain`). Links take the pointing hand and show where they go as a tooltip, and open through the transcript's `openURL`. A prompt's bubble hugs its text unless it holds a box (code, a table), and keeps every line break typed in it (`MarkdownView.parse(lineBreaks:)`). Find in Chat marks the matched words with temporary attributes (`findQuery`, set on matched rows). VoiceOver's headings rotor steps through a reply's headings. The view keeps the width it was measured at (SwiftUI rounds the frame to pixels, and tracking it laid the text out twice per resize step), sets its text before SwiftUI first sizes it, never scrolls the transcript itself (`scrollRangeToVisible`: after a relayout it took a resize to the start of a reply), and never asks for a layout pass when its text is set (it's set while SwiftUI sizes it: asking from there kept rows being laid out and rebuilt, the bottom anchor moving each time); its code boxes' Copy buttons are placed as it draws. It keeps the sizes it measured for a few widths; a bubble keeps the width its text was measured at, and a width too narrow for a word isn't laid out. Measured on the performance scenario's replies as one 30-section reply: a resize step 15 ms, against 17 ms for the `Text` per block it replaced (`MarkdownBenchmark`, Release, 2026-10-05). Only the blocks from the first one built differently are built again (`BuildKey`: a new parse, or a list whose widest marker grew), and a settled message's text is kept (`settled`, 300 messages or 8 MB).
- Streamed text fades in: in the reply being streamed into (`ThreadModel.streamingReplyID`), what follows the text the old and new tails share fades in over 0.3 s, drawn with temporary attributes on a display link that runs only while something is fading.
- Worktrees: New Chat can start a chat in a new git worktree (`thread/start`'s `worktree`, made by the daemon under `<repo>/.claude/worktrees/`). Archiving or deleting such a chat offers to remove the worktree — only Sundown's own, `.claude/worktrees/tether-<8 hex>` (`WindowModel.sundownWorktree`), never Claude Desktop's beside them — asking again before discarding uncommitted changes (`RPCError.worktreeDirty`) or a branch's commits merged nowhere else (`worktreeUnmerged`), and saying why when removal fails.
- A plan's usage limit (`thread/rateLimit`) is said in the status strip only once it's near or reached; the Session pane shows the gauge.
- The Session pane's Context is one bar of what fills the window, each used category in its own system color over an empty track, the compaction reserve in gray at the end, and the categories listed below with matching dots (`ContextBreakdown`, classified by the SDK's `kind`, never by name except on a Claude Code too old to send it). A stacked Swift Charts bar, not a `Gauge`, which shows one value. Plan Usage is a `Gauge` in `.accessoryLinearCapacity` with its value on the row above: the default style draws a marker that reads as a slider's thumb, and `.linearCapacity` a thick level indicator.
- Notifications are for a chat you aren't looking at: a finished reply (per Settings), and a request, whose notification has Allow and Deny. A request is told about once, though the daemon re-sends a waiting one on every reconnect (`RequestSightings`); its notification is withdrawn when it's resolved anywhere (`sundownRequestResolved`), and Allow or Deny on one answered since quietly says Already answered. A chat on screen gets a VoiceOver announcement for a finished reply, and a request's card takes VoiceOver's focus. UI tests never reach Notification Center.
- The Tasks tab browses the chat's tasks in columns, as Finder's column view does (`TasksPane`): the first column every task, each next one the tasks started by the one selected (an agent's own agents, the commands it ran in the background, found through the call that started each, `TaskNode.tree`), then the selected task's detail; the columns scroll sideways once they don't fit, the detail at least 360 pt, and each column resizes by dragging its divider. Every row is the same: a status dot on the name's line (`TaskStateDot`: blue and pulsing while it runs, red failed, a ring stopped, green done, gray waiting), and under the name what it is (Workflow, Agent, Command, Monitor, MCP Tool, from the SDK's `task_type`) and how long it has run or took; no section headers, what's going first, except a workflow's agents, which are its children (no tasks of their own: they come from its run's snapshot, ids `<call id>/agent/<index>`) in a section per phase, in the phases' order, when there's more than one. A workflow is called by its script's name, never its latest agent's words; agents in no phase come first, with no header; its detail (`WorkflowReport`) is what it's for, what it used and, finished, what it returned, never its script or launch receipt, nor how each phase stands, which its agents' column already says; an agent's detail is its own transcript (`WorkflowAgentTranscript`, folded when its items change), its prompt the script's task alone, de-indented, without the harness's framing or the person's relayed request (`WorkflowAgentPrompt`, which leaves an already unframed prompt as it is), or before there is a transcript what its snapshot says. A workflow's agents can't be stopped alone: Stop above their column stops the workflow. Above each column, its owner's name over a bar colored as the dots by what the column holds (`TaskStatusBar`, its counts in its help), with a glass Stop beside both for a running owner. The detail's header is the task's name and its glass controls (Move to Background while it still holds up its turn, Stop); its body is an agent's own transcript (its prompt, then its items folded as the chat folds them) or, for anything else, what it ran, its last summary and its output. Each fact is said once: a row's dot and time aren't repeated in the detail, nor a column's counts in words. Long names show whole on hover. A background task settling is a notice in the transcript, never the CLI's raw `<task-notification>` message. A workflow agent's own background command (`task/event.ownedBySubagent`) is no notice: in Tasks it sits under that agent (`workflowAgentId`), else under its workflow (`workflowToolUseId`), else nowhere, never at the top (`TaskNode.tree`).
- Progress indicators are transient. Every failed, unavailable, disconnected, or not-loaded path needs an explanatory state and a useful recovery action.
- Previews are part of the product-development workflow; state a preview's canvas should be able to change is `@Previewable @State`, and a preview that varies one setting takes it as `arguments:`. Add representative `#Preview` coverage when adding or materially changing a view; seed samples through the real reducers where practical.

## Task tracking

Work is tracked in GitHub Issues on `AFRUITPIE/tether-app` (private), not in a
checked-in task file. Several agents work on this repository independently and
cannot see each other's transcripts, so the issue list is the shared state.

Use the `gh` CLI:

```sh
gh issue list                      # what is open
gh issue view <n>                  # the full description and discussion
gh issue comment <n> --body "..."  # claim it, or record a finding
gh issue close <n> --comment "..." # say what landed and how it was verified
```

Before starting, claim the issue with a comment so another agent does not
duplicate the work. Record anything you learn that changes the shape of the
task — a wrong assumption, a protocol detail, a rejected approach — as a
comment rather than only in a commit message; the next agent reads the issue,
not your transcript.

Reference the issue in the commit that addresses it (`Fixes #12`) so the log
and the tracker stay tied together. Open a new issue rather than expanding an
existing one when you find something unrelated in passing.

Issues labelled `verify` are changes that are written but not yet confirmed in
the running app. They usually cover motion or system behaviour that previews
cannot show, so they need `RunProject`, not `RenderPreview`.

Server-side work belongs to `AFRUITPIE/tether-server`; use `gh --repo` to file
it there when a change crosses the boundary.

## Commit messages

Commits carry no agent attribution: no `Co-Authored-By` trailer, no "generated
with" footer, no mention of the tool that wrote them. The author is always the
repository owner. Mentions of Claude Code as a product are fine and expected —
this app is a client for it.

## Generated code boundary

`TetherProtocol` is generated in the server repository. Never hand-edit:

```text
../tether-server/Sources/TetherProtocol/Generated.swift
../tether-server/schema/sundown.schema.json
```

Change the Zod protocol definitions and implementation in `tether-server`, run `mise run gen` there, then update app call sites. Protocol unions deliberately preserve unknown future variants; keep forward-compatible fallbacks.

## Build and verification

Server releases, when server code changes:

```sh
cd ../tether-server
mise run compile -- --dev # into dist/ with a -dev stamp
# release: bump package.json's version and merge; approve the staged version on npmjs.com
```

`TETHER_VERSION` comes from `package.json`, and the daemon replaces a running one only when that string differs. It is deliberately not the Agent SDK version: a server fix has to be able to ship without waiting for an SDK release. `AGENT_SDK_VERSION` is exported and reported separately.

Releases happen on merge, down a chain: a new Agent SDK becomes a tether-server PR (its `sdk-update.yml`); merging a server version bump releases it to npm, staged until approved; a newly published server becomes a PR here (`server-update.yml`, daily: `ServerRelease.version`, both `Package.resolved` pins, and the app's next patch version and build); merging an app version bump releases the app (`release.yml`: `Scripts/release.sh` on a macOS runner, signed with Developer ID and notarized, once the owner approves it in the `release` environment, which holds the signing secrets and is limited to main; a PR's Release preview check says whether merging it releases). Main stays at the released version between releases: bumping it is deciding to release; and `release.yml` then starts the tap's update (`AFRUITPIE/homebrew-tap`, `brew install --cask afruitpie/tap/sundown`), which moves its cask to the newest release (the tap also checks daily). `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` are set only on the app target, which the workflows read. `release.yml` needs the secrets it lists (the Developer ID certificate as .p12, an App Store Connect API key for notarizing, and `TAP_TOKEN`, which can start the tap's workflow); `Scripts/release.sh` also runs locally, with a Developer ID certificate and `xcrun notarytool store-credentials sundown`. Hardened runtime is on; the sandbox is off, since the app runs `ssh` and login shells. `Scripts/release.sh --beta [<pull request> | <branch>]` makes a beta of a pull request, a branch or the checkout the same way, on this Mac: a pre-release `v<version>-beta.<UTC time>`, and the tap's `sundown@beta` cask (which the script writes, and which conflicts with `sundown`, since it is the same app) moved to it. The tap's daily update follows only full releases.

Use Xcode 27 MCP as the primary app workflow. Open `Sundown.xcodeproj`, then use the Xcode tools rather than raw `xcodebuild` or a separately launched LLDB session:

- `BuildProject` for app builds and diagnostics.
- `RenderPreview` for deterministic view verification and visual variants.
- `RunProject` with `attachDebugger: true` for the real app.
- `InvokeDebuggerCommand` and `GetConsoleOutput` for crashes, exceptions, and runtime warnings.
- Keep `SUNDOWN_OPEN_THREAD=<id>` in the shared scheme when a repeatable launch target is needed, and disable it again before finishing unless the change is intentional.

Always look at the rendered or running UI after a UI change. A clean compile is not visual verification. Confirm that the inspected window belongs to the run you started; multiple stale Sundown instances have previously caused false conclusions.

Package tests:

```sh
swift test --package-path SundownKit
```

The shared Xcode scheme also contains `SundownAppUITests`. Its launch sets
`SUNDOWN_UI_TEST_MODE=1`, which uses an in-process JSON-RPC fixture and fails closed before any
daemon or SSH launch. The PR workflow runs it on `xcode-27` and resolves the public
SwiftPM protocol package without a repository secret. A launch costs seconds, so each test is one
launch walking one flow (`SundownUITestCase` in `UITestSupport.swift` holds the launch and the shared
queries), checking each step with a message that names it; add a check to the flow that already
launches its scenario rather than a test of its own, and keep logic (ordering, formatting, what's
kept across launches) in the package tests. Scenarios (`SUNDOWN_UI_TEST_SCENARIO`): none (one short
chat), `performance` (three long chats; `SUNDOWN_PERF_TURNS` shortens them), `connect-failure`,
`permission`, and `prompts` (a permission, another, a question, a form and a too-long question, each
asked once the one before is answered, each answer said in the chat). `SUNDOWN_UI_TEST_FAIL=a,b`
makes the fixture answer those methods with an error.

`SundownPerformanceUITests` (in the same target) measures hitches with
`XCTHitchMetric` while it drives the inspector, its tabs, the sidebar, chat switching, a window
resize and a streamed reply, against the fixture's `performance` scenario: a 30-turn chat shaped
like real work, and a long working reply for each prompt. Run it with the Sundown Performance scheme, which builds the tests in Release
(Apple: performance testing belongs in an optimized build; the main scheme skips the class, and CI
too), and read the hitch time ratio in the report. The fixture (`UITestFixture`,
`AppModel.uiTestFixture`) is compiled into every build for this, inert unless the app is launched
with `SUNDOWN_UI_TEST_MODE=1`; Apple counts 10 ms/s or less as good. The tests also record the app's CPU,
memory and disk writes, and `XCTOSSignpostMetric` for Chat Switch, History Load and Reply; `testLaunch`
covers launch until responsive plus the Launch signpost, `testIdle` 10 s with no queries. The scheme
tests without the debugger. The fixture's performance turns send turn/started and turn/completed, and
its two other chats are followed, so each switch reloads them. Keep in mind when reading
the numbers:

- The harness adds to them: every query or key press takes an accessibility snapshot of the whole
  app on its main thread, and accessibility stays on for the run. An interaction the app drives
  itself hitches about half as much.
- A live resize of an empty SwiftUI `NavigationSplitView` window already measures about 230 ms/s
  this way, so compare a resize with that, not with zero.
- The window is set to 1000×740 first; how much of the transcript wraps again depends on its width.
- The inspector's tabs live in the pane, not the toolbar: in the toolbar, any change of tab made
  AppKit re-tile the whole toolbar (about 50 ms/s more on this test), however the picker was hosted
  (a stack, a fixed size, item ids).
- Find elements with `element(boundBy: 0)`, not `firstMatch`, after the window's root `TabView`
  switches tabs: `firstMatch`'s shortcut through the tree then misses elements a whole query finds.
- `Self._logChanges()` in the view bodies, with `log stream --predicate 'category == "Changed Body
  Properties"'`, shows which views a test updates and why, where the SwiftUI instrument can't be
  used from the command line.

Signposts (subsystem `com.haydenhong.Sundown`): Connection ▸ Connect (Bootstrap, Handshake and Catalog
events); RPC ▸ RPC (the method as its message); Transcript ▸ History Load, Older Page, Reply (an animation
interval per turn) and Flush (an event per applied batch, with its size); PointsOfInterest ▸ Launch
(didFinishLaunching until the first window's chat is loaded, New Chat, or 30 s) and Chat Switch (a
window's selection until `loadRequestedThread` finishes). In Instruments add os_signpost and filter by
the subsystem. Live: `/usr/bin/log stream --level debug --signpost --predicate 'subsystem ==
"com.haydenhong.Sundown"'` (the full path: zsh has a `log` builtin), which also shows the connection log.
MetricKit's reports are kept in `~/Library/Caches/com.haydenhong.Sundown/MetricKit` (the latest 30;
Debug ▸ MetricKit ▸ Simulate MetricKit Payloads writes samples).

Micro-benchmarks (Markdown parsing, rows, Find, diffs, a streamed reply) are skipped unless
`SUNDOWN_BENCH=1`: `SUNDOWN_BENCH=1 swift test -c release -Xswiftc -DDEBUG -Xswiftc -enable-testing
--package-path SundownKit --filter Benchmark`, compared with the parent commit on the same Mac.

The published package, end to end: `SUNDOWN_NPX_E2E=1 swift test --package-path SundownKit --filter npxRunsThePinnedPackage` runs the pinned version with npx under the login shell, once it's on npm.

Live tests use a real Claude CLI session and can incur cost:

```sh
SUNDOWN_E2E=1 swift test --package-path SundownKit
```

They run the server named by `TETHER_SERVER_BIN` in an isolated `TETHER_HOME`; to test a server working copy, set it to `bun run ../tether-server/src/cli.ts` (with bun's full path). They use Sonnet at low effort.

Do not run live/E2E tests unless their cost and external effects are warranted by the task. SSH end-to-end testing is currently deferred unless explicitly requested.

## Change discipline

- Read both repositories before changing a cross-boundary behavior.
- Preserve unrelated working-tree changes and Xcode user state.
- Keep changes small and coherent. Do not rewrite history, delete sessions, terminate user-owned app instances, or change host configuration without explicit direction.
- Update this guide when architecture or settled UI rules change.
